# RenderDoc 魔改技术文档 — 绕过 ACE 反外挂截帧 UE5 D3D12 游戏

## TL;DR

对 RenderDoc v1.x 源码进行深度定制，实现在腾讯 ACE 反外挂保护下对 UE5 D3D12 游戏（《洛克王国：世界》）的 GPU 截帧。核心技术路线：

1. **特征消除**：全局重命名 RenderDoc 所有二进制标识（DLL 名、导出符号、窗口类名、共享内存名、PE 资源等），消除静态特征码检测
2. **DLL Proxy 注入**：编写 `dxgi.dll` proxy DLL，利用 Windows DLL 搜索顺序劫持（exe 目录优先于 System32），在游戏进程中加载 RenderDoc 核心 DLL
3. **反检测规避**：在 DllMain 中通过磁盘文件重命名（`MoveFileW`）+ PEB 模块名伪装（`BaseDllName`/`FullDllName` 覆写），从 用户态 PEB 枚举、内核态 `NtQueryVirtualMemory`、磁盘文件扫描三个维度同时隐藏 proxy DLL 的真实文件名
4. **Inline Hook 修正**：修改 RenderDoc 的 MinHook inline hook 逻辑，在存在同名 proxy DLL 和 System32 DLL 时，优先选择 System32 模块作为 hook 目标，避免递归调用

最终效果：ACE 无弹窗，API 显示 D3D12，F12 截帧成功。

## 1. 实现原理

### 1.1 整体架构

```
游戏启动器
  └─ NRC-Win64-Shipping.exe（游戏进程）
       │
       │  LoadLibrary("dxgi.dll")      ← UE5 动态加载，非隐式导入
       │  Windows DLL 搜索顺序：exe目录 > System32
       ▼
  [proxy dxgi.dll]（游戏目录）
       │
       │  DllMain(DLL_PROCESS_ATTACH):
       │  ├─ LoadLibrary(System32\dxgi.dll)   ← 真正的 DXGI
       │  ├─ CacheAllRealProcs()              ← 缓存 20 个真实函数指针（在 IAT hook 之前）
       │  └─ ShouldEnableProxyInjectionForProcessPath()
       │       ├─ 普通宿主进程：
       │       │   ├─ LoadLibrary(System32\d3d12.dll)
       │       │   ├─ MoveFileW(dxgi.dll → dxgi.dll.tmp)
       │       │   ├─ MasqueradeModuleName → "mfplat.dll"
       │       │   └─ LoadLibrary(rendertest.dll)
       │       │       ├─ RegisterHooks / EndHookRegistration
       │       │       ├─ HookAllModules() — IAT hook
       │       │       └─ MinHook inline hook:
       │       │            ├─ System32\dxgi.dll  → CreateDXGIFactory/1/2
       │       │            └─ System32\d3d12.dll → D3D12CreateDevice
       │       └─ RenderDoc 工具进程：保留公共 DXGI 转发，跳过 D3D12 预加载、伪装和捕获注入
       │
       ▼
  游戏调用 CreateDXGIFactory2()
       → proxy 导出函数 → 缓存指针 → System32 dxgi.dll 入口
       → 但入口已被 MinHook patch 为 jmp(E9) → RenderDoc hook 函数
       → hook 调用 trampoline 获取真实 factory → HandleWrap 包装
       → 返回 WrappedIDXGIFactory 给游戏
       → 后续 D3D12CreateDevice 同理被拦截包装
       → RenderDoc 截帧生效
```

### 1.2 为什么选择 dxgi.dll 作为 Proxy 目标

| 条件 | dxgi.dll | version.dll | 游戏自带 DLL |
|------|----------|-------------|-------------|
| 不在 Windows KnownDLLs 列表 | 是 | 是 | N/A |
| exe 目录优先加载 | 是（LoadLibrary 动态加载） | 是 | N/A |
| 与图形 API 直接相关 | 是（DXGI 是 D3D 的基础设施） | 否 | 否 |
| RenderDoc hook 时机 | 完美（在任何 D3D 调用之前） | 太晚或不确定 | 不可控 |
| ACE 黑名单 | 是（需额外规避） | 是 | 有完整性校验 |

关键优势：dxgi.dll 是 UE5 通过 `FPlatformProcess::GetDllHandle("dxgi.dll")` 即 `LoadLibrary` 动态加载的，proxy 的 DllMain 在游戏调用任何 DXGI/D3D12 函数之前执行，确保 RenderDoc 的 inline hook 能在最早时机安装。

### 1.3 ACE 反外挂检测模型

经逆向测试，ACE（腾讯安全反外挂系统）在该游戏中的 DLL 检测机制包含以下层次：

| 检测维度 | 检测手段 | 信息来源 |
|---------|---------|---------|
| 用户态模块枚举 | 遍历 PEB `InLoadOrderModuleList`，检查 `BaseDllName` | 用户态，可被 PEB 伪装绕过 |
| 内核态文件名查询 | `NtQueryVirtualMemory(MemoryMappedFilenameInformation)` 读取 section object 文件名 | 内核态，需磁盘重命名才能更新 |
| 磁盘文件扫描 | 扫描游戏目录下的文件名，匹配黑名单 | 文件系统，需磁盘重命名 |
| 文件完整性校验 | 游戏自带 DLL 的哈希校验 | 启动器/ACE 合作 |
| 文件名黑名单 | `version.dll`、`dxgi.dll` 等已知系统 DLL 劫持文件名 | 内置规则库 |
| 进程注入检测 | 拦截 `CreateRemoteThread`、`NtWriteVirtualMemory` 等 | 内核驱动 `tpstackflt.sys` |

### 1.4 三层规避策略

针对上述检测模型，最终方案在三个维度同时规避：

```
                        ┌──────────────────────────────────┐
                        │  ACE 检测不到 "dxgi.dll" 的原因   │
                        └──────────────────────────────────┘
                                       │
              ┌────────────────────────┼────────────────────────┐
              ▼                        ▼                        ▼
   PEB 模块名伪装              磁盘文件重命名             不使用远程注入
   BaseDllName →              dxgi.dll →                 DLL proxy 自加载
   "mfplat.dll"               dxgi.dll.tmp               无需 CreateRemoteThread
   FullDllName →              内核 section object         游戏主动 LoadLibrary
   "C:\Windows\               文件名同步更新              tpstackflt.sys 无从拦截
    System32\mfplat.dll"
```

## 2. 实现步骤

### 2.1 第一阶段：特征消除（静态特征码重命名）

目的：消除所有与 "renderdoc" 相关的字符串特征，防止 ACE 通过字符串扫描/导出表扫描/PE 资源信息检测到 RenderDoc 的存在。

**重命名规则**：`renderdoc` → `rendertest`，`RenderDoc` → `RenderTest`，`RENDERDOC` → `RENDERTEST`

涉及 7 大类共约 40 处修改：

| 类别 | 关键修改点 | 影响 |
|------|-----------|------|
| 核心 DLL 标识符 | `renderdoc__replay__marker()` → `rendertest__replay__marker()` | replay 进程识别 |
| 可执行文件路径硬编码 | `renderdoccmd.exe` → `rendertestcmd.exe`（6 处） | 进程创建/注入 |
| Shim DLL 路径 | `renderdocshim32/64.dll` → `rendertestshim32/64.dll` | 全局 hook |
| 进程白名单 | `renderdoccmd.exe` / `qrenderdoc.exe` → 对应 rendertest 版本 | 避免自注入 |
| 崩溃处理命名对象 | `RENDERDOC_CRASHHANDLE` → `RENDERTEST_CRASHHANDLE` | 命名内核对象 |
| PE 资源/窗口类名 | `ProductName: RenderDoc` → `RenderTest`，`renderdocGLclass` → `rendertestGLclass` | PE 版本信息、OpenGL 窗口类 |
| VS 项目输出名 | `renderdoc.dll` → `rendertest.dll`，`renderdoccmd.exe` → `rendertestcmd.exe` 等 | 编译产物文件名 |

**关键细节**：`REPLAY_PROGRAM_MARKER()` 宏定义的导出符号是 RenderDoc DLL 判断当前进程是 replay 环境还是目标游戏进程的核心依据。如果 DLL 与 EXE 导出的 marker 符号不一致，DLL 会误判当前为游戏进程，在 UI 进程中注入 GPU hook，导致 UI 崩溃。因此 DLL 和所有 EXE 必须同步修改。

### 2.2 第二阶段：注入方式探索

#### 2.2.1 SetThreadContext 线程劫持注入（替代 CreateRemoteThread）

修改 `win32_process.cpp` 中的 `InjectDLL()` 函数：

```
原始方式：CreateRemoteThread + LoadLibraryW
  → 被 ACE 内核驱动 tpstackflt.sys 直接拦截

新方式：SetThreadContext 劫持主线程 RIP
  1. CreateToolhelp32Snapshot 枚举目标进程线程，按创建时间排序找主线程
  2. SuspendThread 挂起主线程
  3. GetThreadContext 保存原始 CONTEXT（特别是 RIP）
  4. VirtualAllocEx 在远程进程分配 shellcode 内存
  5. 写入 x64 shellcode：
     sub rsp, 0x28        ; 对齐栈 + shadow space
     mov rcx, <dllPath>   ; LoadLibraryW 参数
     mov rax, <LoadLibraryW>
     call rax
     add rsp, 0x28
     jmp <originalRIP>    ; 返回原始执行流
  6. SetThreadContext 将 RIP 指向 shellcode
  7. ResumeThread，轮询 RIP 是否返回原始位置
  8. 失败时 fallback 到 CreateRemoteThread
```

**结果**：ACE 内核驱动 `tpstackflt.sys` 同样拦截了此方式。所有基于远程进程操作的注入方式（`CreateRemoteThread`、`SetThreadContext`、`NtQueueApcThread` 等）都被内核层 hook 拦截。

#### 2.2.2 DLL Proxy 方案（最终采用）

放弃远程注入，改用 DLL 搜索顺序劫持。游戏自己 `LoadLibrary` 加载 proxy DLL，属于进程内的正常 DLL 加载行为，内核驱动无法区分是正常加载还是恶意注入。

### 2.3 第三阶段：dxgi.dll Proxy 实现

#### 2.3.1 Proxy DLL 结构

```c
// version_proxy.cpp — 核心结构

// 1. 全局缓存：20 个真实 dxgi.dll 函数指针
static HMODULE g_hRealDxgi = NULL;
static PFN_CreateDXGIFactory  g_real_CreateDXGIFactory  = NULL;
static PFN_CreateDXGIFactory  g_real_CreateDXGIFactory1 = NULL;
static PFN_CreateDXGIFactory2 g_real_CreateDXGIFactory2 = NULL;
// ... 共 20 个

// 2. DllMain — 核心初始化流程（严格顺序执行）
BOOL APIENTRY DllMain(HMODULE hModule, DWORD reason, LPVOID lpReserved) {
    if (reason == DLL_PROCESS_ATTACH) {
        wchar_t processPath[MAX_PATH] = {};
        GetModuleFileNameW(NULL, processPath, MAX_PATH);
        const bool enableProxyInjection =
            ShouldEnableProxyInjectionForProcessPath(processPath);

        // 所有进程都需要真实 DXGI 转发
        LoadLibraryW("C:\\Windows\\System32\\dxgi.dll");
        CacheAllRealProcs();

        // 普通宿主默认启用；RenderDoc UI/命令行工具被精确排除
        if (enableProxyInjection) {
            LoadLibraryW("C:\\Windows\\System32\\d3d12.dll");
            MoveFileW("dxgi.dll", "dxgi.dll.tmp");
            MasqueradeModuleName(hModule, L"mfplat.dll", ...);
            LoadLibraryW("rendertest.dll");
        }
    }
}

// 3. 导出函数 — 转发到缓存指针
__declspec(dllexport) HRESULT WINAPI CreateDXGIFactory2(UINT Flags, REFIID riid, void **ppFactory) {
    return g_real_CreateDXGIFactory2(Flags, riid, ppFactory);
    // 注意：g_real_CreateDXGIFactory2 指向的 System32 dxgi.dll 入口
    // 此时已被 MinHook patch 为 jmp → RenderDoc hook 函数
}
```

#### 2.3.2 导出表定义（version_proxy.def）

```def
LIBRARY "dxgi"
EXPORTS
    CreateDXGIFactory                @10
    CreateDXGIFactory1               @11
    CreateDXGIFactory2               @12
    DXGIGetDebugInterface1           @19
    DXGIDeclareAdapterRemovalSupport @17
    ; ... 共 20 个导出函数，序号与系统 dxgi.dll 一致
```

#### 2.3.3 PEB 模块名伪装实现

```c
static void MasqueradeModuleName(HMODULE hModule, const wchar_t *newBaseName,
                                  const wchar_t *newFullPath) {
    // 通过 TEB 获取 PEB 指针
    // x64: __readgsqword(0x60)  |  x86: __readfsdword(0x30)
    PPEB peb = (PPEB)__readgsqword(0x60);

    // 遍历 PEB->Ldr->InLoadOrderModuleList 双向链表
    MY_PEB_LDR_DATA *ldr = (MY_PEB_LDR_DATA *)peb->Ldr;
    LIST_ENTRY *head = &ldr->InLoadOrderModuleList;

    // 遍历找到 DllBase == hModule 的 LDR_DATA_TABLE_ENTRY
    // 直接覆写 BaseDllName.Buffer 和 FullDllName.Buffer
    // 注意：新名字长度必须 <= MaximumLength，否则越界写入
    memset(entry->BaseDllName.Buffer, 0, entry->BaseDllName.MaximumLength);
    memcpy(entry->BaseDllName.Buffer, newBaseName, baseLen);
    entry->BaseDllName.Length = (USHORT)baseLen;
    // FullDllName 同理
}
```

**技术要点**：
- `winternl.h` 只暴露了 `InMemoryOrderModuleList`，需要自定义完整的 `PEB_LDR_DATA` 和 `LDR_DATA_TABLE_ENTRY` 结构体
- PEB 伪装本身只能骗过用户态的模块枚举 API（如 `EnumProcessModules`），无法影响内核态的 `NtQueryVirtualMemory(MemoryMappedFilenameInformation)`
- 必须配合磁盘文件重命名才能完整规避

### 2.4 第四阶段：RenderDoc Inline Hook 修正

#### 2.4.1 问题：同名模块冲突

当进程中同时存在 proxy `dxgi.dll`（游戏目录）和真实 `dxgi.dll`（System32），RenderDoc 的 `ForAllModules` 枚举时会产生两个同名模块。原始逻辑中先匹配到的模块成为 `DllHooks["dxgi.dll"].module`，后来的进入 `altmodules`。

##### 修复前（错误状态）：MinHook 把 hook 装在 proxy 上

```
进程内存布局：
┌─────────────────────────────────────────────────────────────────────┐
│  游戏目录\dxgi.dll（proxy）                     ← module（先被枚举）  │
│  ┌──────────────────────────────────────────┐                       │
│  │ CreateDXGIFactory2:                       │                       │
│  │   [E9 xx xx xx] jmp → RenderDoc hook ←── │── MinHook 错误地 patch│
│  │                 ↑                         │   了这里！            │
│  │         (无效！游戏通过缓存指针绕过此处)    │                       │
│  └──────────────────────────────────────────┘                       │
│                                                                      │
│  System32\dxgi.dll（真实）                      ← altmodules[0]     │
│  ┌──────────────────────────────────────────┐                       │
│  │ CreateDXGIFactory2:                       │                       │
│  │   [48 89 5C 24 08] mov [rsp+8], rbx       │ ← 原始代码，未被 hook  │
│  │   ...                                     │                       │
│  └──────────────────────────────────────────┘                       │
└─────────────────────────────────────────────────────────────────────┘

调用链：
游戏 → proxy::CreateDXGIFactory2()
     → g_real_CreateDXGIFactory2（缓存指针，指向 System32 入口）
     → System32 入口（未被 hook）
     → 直接返回真实 factory        ← RenderDoc 完全被绕过！
```

##### 修复后（正确状态）：MinHook 把 hook 装在 System32 上

```
进程内存布局：
┌─────────────────────────────────────────────────────────────────────┐
│  游戏目录\dxgi.dll（proxy，已伪装为 mfplat.dll）                      │
│  ┌──────────────────────────────────────────┐                       │
│  │ CreateDXGIFactory2:                       │                       │
│  │   call g_real_CreateDXGIFactory2 ─────────│──────────────────┐  │
│  └──────────────────────────────────────────┘                   │  │
│                                                                  │  │
│  System32\dxgi.dll（真实）                     ← hookModule      │  │
│  ┌──────────────────────────────────────────┐                   │  │
│  │ CreateDXGIFactory2:                       │ ←────────────────┘  │
│  │   [E9 xx xx xx] jmp → RenderDoc hook  ←──│── MinHook 正确 patch │
│  │                                           │   了这里！           │
│  │   [trampoline: 原始字节 + jmp回来]         │                      │
│  └──────────────────────────────────────────┘                       │
└─────────────────────────────────────────────────────────────────────┘

调用链：
游戏 → proxy::CreateDXGIFactory2()
     → g_real_CreateDXGIFactory2（缓存指针，指向 System32 入口）
     → System32 入口：[E9 xx] jmp → RenderDoc::CreateDXGIFactory2_hook
     → hook 调用 trampoline → 真实 factory 创建
     → HandleWrap → 返回 WrappedIDXGIFactory   ← 截帧生效！
```

#### 2.4.2 修改：优先选择 System32 模块

在 `win32_hook.cpp` 的 inline hook 安装阶段新增模块选择逻辑：

```cpp
// win32_hook.cpp — inline hook 安装时的模块选择
HMODULE hookModule = it->second.module;
{
    wchar_t sysDir[MAX_PATH];
    GetSystemDirectoryW(sysDir, MAX_PATH);
    size_t sysDirLen = wcslen(sysDir);

    // lambda: 检查模块是否来自 System32
    auto tryPreferSystem = [&](HMODULE mod) {
        wchar_t modPath[MAX_PATH] = {};
        GetModuleFileNameW(mod, modPath, MAX_PATH - 1);
        if (_wcsnicmp(modPath, sysDir, sysDirLen) == 0) {
            hookModule = mod;
            return true;
        }
        return false;
    };

    // 先检查主模块，再遍历 altmodules
    if (!tryPreferSystem(hookModule)) {
        for (size_t ai = 0; ai < it->second.altmodules.size(); ai++) {
            if (tryPreferSystem(it->second.altmodules[ai]))
                break;
        }
    }
}

// 直接从 hookModule GetProcAddress 获取函数地址，不使用 *hook.orig
// 因为 *hook.orig 可能在 ApplyHooks 阶段被设为 proxy 的地址
void *target = (void *)GetProcAddress(hookModule, hook.function.c_str());
```

## 3. 踩坑细节

### 3.1 递归调用风暴（9 万次 CreateDXGIFactory）

**现象**：游戏启动后 `CreateDXGIFactory` 被调用约 9 万次，栈溢出崩溃。

**根因分析**：

```
调用链路：
游戏 → proxy::CreateDXGIFactory2()
     → GetProcAddress(g_hRealDxgi, "CreateDXGIFactory2")  ← 运行时获取
     → 但 rendertest.dll 已经 IAT hook 了 proxy 的 GetProcAddress
     → Hooked_GetProcAddress 检查到 dxgi.dll 的 CreateDXGIFactory2 已注册 hook
     → 返回 hook 后的地址（RenderDoc 的 CreateDXGIFactory2_hook）
     → proxy 调用的实际是 RenderDoc hook 函数
     → RenderDoc hook 调用 trampoline → 回到 System32 dxgi.dll
     → System32 入口也被 MinHook patch → 又跳回 RenderDoc hook
     → 无限递归
```

**修复**：在 `rendertest.dll` 加载之前（即 IAT hook 安装之前），就通过 `GetProcAddress` 缓存所有 20 个真实函数指针到全局变量。proxy 的导出函数直接使用缓存指针，不再运行时调用 `GetProcAddress`。

```c
// DllMain 中的执行顺序（修复后）：
LoadLibrary(System32\dxgi.dll);
CacheAllRealProcs();           // ← 此时 IAT 尚未被 hook，GetProcAddress 返回真实地址
LoadLibrary(rendertest.dll);   // ← IAT hook 安装，但已不影响缓存的指针
```

### 3.2 Inline Hook 装在 Proxy 上而非 System32 上

**现象**：RenderDoc 日志显示 hook 安装成功，但截帧时 API 显示 None。

**根因**：`ForAllModules` 枚举时 proxy dxgi.dll 先被发现（因为在游戏目录，加载地址更靠前），成为 `DllHooks["dxgi.dll"].module`。MinHook 从这个 module 的 `GetProcAddress` 获取函数地址并 patch——实际 patch 的是 proxy 的导出函数，而不是 System32 的函数入口。

游戏通过 proxy 调用 → proxy 用缓存指针调用 System32 → System32 入口未被 hook → 直接返回真实结果 → RenderDoc 完全被绕过。

**修复**：在 inline hook 安装阶段遍历 `altmodules`，优先选择路径以 `C:\Windows\System32\` 开头的模块（见 2.4.2 节）。

### 3.3 *hook.orig 指向错误地址

**现象**：修复模块选择后，部分 hook 仍然安装在 proxy 上。

**根因**：`ApplyHooks` 阶段（IAT hook）中，`*hook.orig` 被设置为 `GetProcAddress(proxyModule, func)` 的返回值。在后续 inline hook 阶段，代码检查 `if(*hook.orig == NULL)` 来决定是否重新获取地址——由于已经有值（proxy 的地址），条件为 false，跳过了从 System32 模块重新获取。

**修复**：inline hook 阶段无条件从 `hookModule`（已确认为 System32）重新 `GetProcAddress`，忽略 `*hook.orig` 的旧值。

### 3.4 D3D12CreateDevice 未被 Hook

**现象**：DXGI Factory 创建被拦截，但 `D3D12CreateDevice` 没有被 hook，导致 RenderDoc 无法包装 D3D12 设备。

**根因**：`d3d12.dll` 在 UE5 中是 delay-load 的。当 `rendertest.dll` 初始化并调用 `ForAllModules` / `HookAllModules` 时，`d3d12.dll` 尚未被加载，因此 `DllHooks["d3d12.dll"].module == NULL`，inline hook 直接跳过。

**修复**：在 proxy 的 DllMain 中，加载 System32 dxgi.dll 之后立即加载 System32 d3d12.dll：

```c
// DllMain Step 1:
LoadLibraryW(L"C:\\Windows\\System32\\dxgi.dll");
LoadLibraryW(L"C:\\Windows\\System32\\d3d12.dll");  // ← 确保 rendertest.dll 初始化时能找到
```

### 3.5 version.dll 被 ACE 黑名单检测

**现象**：使用 `version.dll` 作为 proxy 时，游戏成功启动并进入主界面，rendertest.dll 也成功加载，但约 10 秒后 ACE 弹窗 "安全系统检测到非法劫持模块，请删除 version.dll"。

**根因**：ACE 维护了一个已知系统 DLL 劫持文件名黑名单（`version.dll`、`dxgi.dll`、`d3d11.dll` 等），会扫描游戏目录和已加载模块列表。

**修复**：改用 `dxgi.dll`（虽然也在黑名单中，但配合磁盘重命名 + PEB 伪装可以规避）。选择 `dxgi.dll` 而非其他 DLL 的原因是它与图形 API 直接相关，hook 时机最优。

### 3.6 PEB 伪装单独不够

**现象**：仅做 PEB 模块名伪装（`BaseDllName` 改为 `mfplat.dll`），ACE 仍然检测到 `dxgi.dll`。

**根因**：ACE 不仅通过 PEB 枚举检测模块，还可能使用 `NtQueryVirtualMemory(MemoryMappedFilenameInformation)` 直接查询内核中 section object 的文件名。PEB 伪装只影响用户态数据结构，内核层面的文件名映射不受影响。

**修复**：在 PEB 伪装之前先执行 `MoveFileW` 磁盘重命名。Windows 的 section object 持有的是文件对象的引用，文件重命名后 `NtQueryVirtualMemory` 返回的路径也会更新。

### 3.7 PluginCrosCurl.dll 替换方案失败

**现象**：将游戏自带的 `PluginCrosCurl.dll` 替换为 proxy 后，启动器检测到文件被修改，弹出"修复"按钮。

**根因**：启动器/ACE 对游戏自带 DLL 有文件完整性校验（哈希校验），任何修改都会被检测到。

**结论**：不能替换游戏已有的任何 DLL，只能新增不在黑名单中的 DLL。

### 3.8 XAudio2_9Redist.dll Proxy 方案失败

**现象**：使用 `XAudio2_9Redist.dll`（不在 ACE 黑名单中）作为 proxy，但 rendertest.dll 未成功加载。

**根因**：
1. XAudio2 是 delay-load 的，触发时间远晚于 DXGI 加载——此时图形 API 的初始化已经完成，hook 时机已过
2. `XAudio2Create` 返回失败后 delay-load helper 会调用 `FreeLibrary` 卸载 proxy
3. 即使用 `GET_MODULE_HANDLE_EX_FLAG_PIN` 阻止卸载，真正的游戏进程可能根本不会触发 XAudio2 的 delay-load

### 3.9 编译踩坑

| 问题 | 原因 | 解决方案 |
|------|------|---------|
| C4819 编译错误 | 源码含非 ASCII 字符（中文注释等），默认编码不兼容 | `renderdoc.vcxproj` 添加 `/utf-8` 编译选项 |
| `vk_wsi_funcs.cpp` ICE 崩溃 | MSVC WholeProgramOptimization 优化器内部错误 | 关闭 WholeProgramOptimization |
| 注入 32 位进程报错 | 只编译了 x64，缺少 Win32 版本的 shim DLL | 同时编译 x64 和 Win32 配置 |
| Global Hook 报 "renderdoccmd not found" | 路径中包含中文/特殊字符，short path 未启用 | 启用 F 盘的 8.3 短文件名支持 |

## 4. 做了哪些尝试（完整时间线）

### 尝试 1：直接使用官方 RenderDoc — 失败

直接使用官方 RenderDoc 下载版，游戏检测到并弹窗"启用了黑客工具"。ACE/CrashSight 通过扫描进程模块列表中的 `renderdoc.dll` 导出符号和文件名检测。

### 尝试 2：特征重命名 + Launch 启动 — 失败

特征重命名完成后绕过了检测弹窗，但：
- 直接 Launch 游戏 exe → 报"缺失游戏文件"（必须走启动器）
- Launch 启动器 → 游戏启动但注入无效，Attach 列表为空

### 尝试 3：特征重命名 + Global Process Hook — 失败

Global Hook 依赖 `rendertestcmd.exe` 进程和 shim DLL，路径中的中文字符导致 short path 问题。修复 short path 后 hook 仍然无法注入，ACE 内核驱动拦截。

### 尝试 4：特征重命名 + rendertestcmd inject 命令 — 失败

报 "Failed to inject rendertest.dll into process"。底层使用 `CreateRemoteThread + LoadLibraryW`，被 `tpstackflt.sys` 拦截。

### 尝试 5：SetThreadContext 线程劫持注入 — 失败

用 shellcode 劫持主线程 RIP 来加载 DLL。ACE 内核驱动同样拦截了 `SetThreadContext` 操作。

**结论：所有基于远程进程操作的注入方式在 ACE 保护下均不可行。**

### 尝试 6：version.dll Proxy — 部分成功

version.dll proxy 成功加载 rendertest.dll，游戏启动并进入主界面，Attach 列表可见。但 ACE 在运行时扫描到 `version.dll` 文件名，弹窗"检测到非法劫持模块"。

**关键发现**：自定义名字的 DLL（如 `rendertest.dll`）不被 ACE 检测，说明 ACE 使用的是文件名黑名单而非通用的未知 DLL 检测。

### 尝试 7：PluginCrosCurl.dll 替换 — 失败

替换游戏自带 DLL 被启动器的完整性校验拦截。

### 尝试 8：XAudio2_9Redist.dll Proxy — 失败

时机太晚，且 delay-load 卸载机制导致 proxy 被释放。

### 尝试 9：dxgi.dll Proxy（无反检测） — 部分成功

技术完全可行：API 显示 D3D12，截帧生效。但 ACE 约 10 秒后检测到 `dxgi.dll` 并杀进程。

### 尝试 10：dxgi.dll Proxy + PEB 伪装 — 失败

仅 PEB 伪装不够，ACE 通过 `NtQueryVirtualMemory` 从内核层面读取真实文件名。

### 尝试 11：dxgi.dll Proxy + 磁盘重命名 + PEB 伪装 — 成功

三层规避同时生效：
- 磁盘文件名：`dxgi.dll.tmp`（不在黑名单）
- PEB 模块名：`mfplat.dll`（正常系统 DLL）
- 内核 section object：跟随磁盘重命名更新

ACE 无弹窗，API 显示 D3D12，F12 截帧成功，游戏正常运行。
